# UI languages (i18n)

The BeeDocs web UI ships in seven languages: **English, Français, Deutsch,
Español, Nederlands, 日本語, 中文（简体）**. Only the UI chrome is translated —
documents, diagrams, commit messages and every other piece of user content stay
exactly as their authors wrote them, and so does everything the server sends
(API error messages, LLM output).

## Choosing a language

Settings → Appearance → **Language**. The choice is per browser
(`localStorage['beedocs-lang']`), like the theme. A browser that never chose
follows `navigator.languages` (first match wins, `zh-CN` → 中文) and falls back
to English. The picker always shows each language's native name — it must stay
readable to someone who can't read the currently active language.

## How it works

Hand-rolled, no i18n library — the same trade theme.tsx makes. Everything lives
in `src/beedocs-web/src/i18n/`:

- `index.tsx` — `I18nProvider` (outermost provider in App.tsx, so the login
  screen and the public reader site translate too), the `useI18n()` hook
  returning `{ lang, setLang, t }`, and a non-React `translate()` for
  module-scope helpers. `t('ns.key', { name })` interpolates `{name}`
  placeholders. The provider also keeps `<html lang>` current.
- `langs.ts` — the `Lang` union and the `LANGUAGES` registry.
- `messages/*.ts` — one file per feature namespace (`nav`, `shell`, `git`,
  `studio`, …), each exporting all seven dictionaries as
  `{ en, fr, de, es, nl, ja, zh } satisfies Record<Lang, Msgs>`.

The type system is the completeness check: in every messages file, `Msgs` is
`Record<keyof typeof en, string>`, so a key translated in English but missing
in, say, Japanese is a **compile error in the file that owns it**. English is
still the runtime fallback for keys mid-edit in dev. `MessageKey` (the union of
every namespace's keys) is what `t()` accepts; dynamically built keys are cast
(`t(`settings.tab.${id}` as MessageKey)`).

`messages/common.ts` is the shared glossary — recurring verbs (Save, Cancel,
Delete…) and the product nouns (Shelf, Book, Page, Diagram…). Feature
namespaces reuse `common.*` keys instead of re-translating them, and new
translations must follow the glossary's terminology so "shelf" is Étagère /
Regal / Estantería / Boekenplank / シェルフ / 书架 everywhere.

## Adding things

- **A key**: add it to the `en` block of the owning namespace file; the
  compiler then forces the other six blocks. Prefix keys with the namespace
  (`'git.pull'`).
- **A namespace**: copy the shape of `messages/common.ts`, register it in the
  `MESSAGES` map in `i18n/index.tsx`. That's all.
- **A language**: add it to `Lang` + `LANGUAGES` in `langs.ts`; the compiler
  then walks you through every messages file that misses it.

## What deliberately stays English

Proper nouns (BeeDocs, BeeDiagram, Markdown, Mermaid, MCP, GitHub, Azure
DevOps, PowerPoint, theme names…), technical identifiers (config keys, env
vars, file extensions, spreadsheet function names, keyboard key caps), code and
config examples, and text that becomes *content* (the prefilled `Update <file>`
commit message, LLM prompts in useLlmAssist — those are API payloads, not UI).
Shape names in the BeeDiagram/isometric catalogs are serialized for the MCP
server (`diagram-catalog.json`, `IsometricCatalog`) and must not be renamed in
the data files; palette labels are translated at render time by keyed lookup
with the catalog name as fallback.

Server-side strings (API validation/error messages) are not translated in v1 —
the UI shows them verbatim. Exported documents (PDF/DOCX/PPTX chrome) also keep
English labels for now.
