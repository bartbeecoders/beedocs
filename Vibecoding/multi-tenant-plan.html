Recommendation

One isolated instance per tenant — not a shared multi-tenant process

Each customer gets their own Kubernetes namespace with its own pod (API + MCP), volume, secrets, hostname and network policy, all running the same BeeDocs image. The application already treats everything as instance-scoped — one SQLite file, five data directories, settings in app_setting, caches in singletons — so an instance is already a complete tenant. What is missing is the tooling to stamp out instances safely and a handful of hardening changes for running on the internet for someone else.

  • Strongest isolation for the least code. A bug in BeeDocs cannot leak data between customers, because no process, file or database is shared.
  • Keeps every future feature cheap. A shared process would put a tenant check in front of every query, cache and file path forever.
  • Cost: roughly 200–350 MB RAM per tenant at idle, plus one rollout per tenant on upgrade. Fine for a handful of customers; revisit if the count heads towards dozens.

Decisions and risks

Open questions for you

  1. How many tenants in the first year, and the VPS’s RAM/disk? Sets the per-tenant budget.
  2. Hostnames: <slug>.docs.<domain> for all, or customer-owned domains too?
  3. Customer sign-in: are local BeeDocs accounts enough, or will a customer want their own SSO (Entra ID / Google)? That would be a new OIDC provider next to RBA.
  4. AI features: does each customer bring their own LLM key, or do you supply one (and absorb its cost)?
  5. Operator access: should you hold a break-glass admin account inside each tenant, or only kubectl access?
  6. Backups: which bucket/provider holds tenant backups, and how long are they kept after a customer leaves?

Risks to watch

  • VPS capacity — every tenant is a .NET process plus the MCP sidecar; one VPS is also one failure domain for all customers.
  • Upgrade drift — pinned versions invite tenants that never upgrade; keep pins temporary.
  • Disk exhaustion — one tenant filling the node’s disk affects all; quotas and alerts are not optional.
  • Misconfigured template — isolation now lives in manifests; the Phase 5 isolation tests must run for every new tenant.
  • Legal — hosting customer documents implies a processing agreement and a data-deletion promise.
